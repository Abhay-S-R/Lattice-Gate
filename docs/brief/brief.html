Unique selling proposition

Shared files outlive the devices, keys and permissions around them, and most systems either keep trusting a lost phone or lock everyone out. Key Identity Guard revokes a lost device on every node in about 33 ms (p50), re-keys the file, and never interrupts colleagues who still need access. Every decision lands in a hash-chained, signed log an operator verifies offline, while a rule-based detector (no AI/ML) explains unapproved privilege changes and lateral movement. All cryptography is NIST post-quantum (ML-KEM-768, ML-DSA-65) from Node's built-in OpenSSL, with zero dependencies, and every claim is a command a judge can re-run.

Architecture

Identity. A device counts only after an approved enrolment and appears in a snapshot that nodes verify with a pinned key. Each request is ML-DSA-65 signed over a domain-separated transcript with a one-time 30 s nonce; nodes check lease, status, nonce, signature, key version and grant, then log the decision. Keys. Each file version has its own AES-256-GCM key, wrapped per device with ML-KEM-768 + HKDF-SHA-256; rotation uses an epoch cutoff with a stated 30 s grace for transfers already authenticated. Recovery. A rotation journal aborts or rolls forward after a crash; backups are refused unless signed, intact and current. Stack. Node.js 24.11.1 (OpenSSL 3.5.4, SQLite 3.50.4), Linux x86-64, no npm dependencies. Everything shown is implemented and tested.

One-page threat model · what we protect, from whom, and what we do not claim

Assets (property that matters)

  • Files and their keys: confidentiality, integrity.
  • Device identity keys: authenticity.
  • Policy and revocation state: integrity, freshness.
  • Audit logs: integrity up to the last signed checkpoint.
  • Backups: integrity, confidentiality, no rollback.
  • Round 1 decisions: correct, no disclosure on deny.

Adversaries and capabilities

  • Hostile caller controlling Round 1 input (any JSON, parallel calls).
  • Lost or revoked device keeping its old keys.
  • Insider with valid credentials escalating or probing services.
  • Network attacker replaying, reordering or altering messages.
  • Offline tamperer editing logs or backups.
  • Future quantum attacker recording traffic now.

Trust boundaries (where identity and permissions are checked)

Worker → adapter: strict validation; actor is a trusted input. Device → node: signed request, one-time nonce, status, grant. Control plane → node: pinned signature, rising epoch, 5 s lease. Operator → control plane: approvals, offline recovery key, external anchor. Device ↔ device: mutually signed handshake with key confirmation.

Assumptions

The control plane and its keys are trusted (key custodian). The operator guards the recovery key and anchor. Nodes share one host and clock; the OS honours fsync; Node 24.11.1 / OpenSSL 3.5.4 are correct; the Round 1 worker supplies actor.

Exclusions and remaining risks

  • Largest risk: the control plane holds file keys. Its compromise exposes files (not messaging sessions, whose keys are ephemeral).
  • Revocation stops future access; copied plaintext cannot be recalled. Its delay is measured, not zero.
  • Round 1 cannot authenticate actor; its state directory is out of scope and stores bodies in plaintext.
  • Low-and-slow and two-edge probes evade the detector (all 20 reported as misses); the benchmark is synthetic.
  • Single-host timings; best-effort memory wiping; no forward secrecy for stored files; no hybrid exchange; no session resumption.
